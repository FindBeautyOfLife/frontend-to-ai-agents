# Tool Calling：让模型使用本地工具

这个示例使用百炼聊天模型和 5 个本地工具，构成一个小型演示商店助手。通过多轮对话展示模型如何选择工具、程序如何执行函数，以及工具结果如何回传给模型，不依赖额外的 Agent 框架。

## 学习目标

读完并运行本示例后，应能解释三个问题：模型如何知道有哪些工具？模型请求调用函数后，谁来执行？工具结果为什么需要回传给模型？

阅读前需要了解 Python 函数、字典、JSON 和基本 HTTP 请求。本阶段是独立命令行程序，不需要启动阶段 02 的 FastAPI 服务。

## 快速开始

需要 Python 3.11+。在本目录创建虚拟环境并安装依赖：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

安装完成后，可以先运行离线测试，验证本地工具和调用流程，无需配置密钥：

```powershell
.\.venv\Scripts\python.exe -m unittest -v
```

测试结束时应显示 `OK`。测试使用模拟模型响应，不会进入交互聊天。

要体验真实模型调用，先复制配置模板（已有 `.env` 时跳过复制）：

```powershell
Copy-Item .env.example .env
```

在 `.env` 中填写 `DASHSCOPE_API_KEY`，并按账号地域和权限设置 `BAILIAN_BASE_URL`、`BAILIAN_MODEL`。所选模型需要支持工具调用（Function Calling）。密钥只交给 SDK 认证，不放进聊天消息；对话和工具结果会发给所配置的模型服务。

配置完成后启动：

```powershell
.\.venv\Scripts\python.exe main.py
```

依次试试：

```text
你好
帮我查一下订单 A1001 的物流
再看看 A1002 的状态
对比 A1001 和 A1003 的状态
查询 A9999
quit
```

普通聊天通常只请求模型一次。查询订单通常是两次：第一次取得工具调用请求，第二次让模型根据查询结果回答。模型也可能分多轮查询。

重点观察终端中的三类日志：`[模型请求]` 表示一次模型接口调用，`[工具请求]` 表示模型希望调用的函数和参数，`[工具结果]` 表示 Python 实际执行后的返回值。查询 A1001 应得到“已发货”；查询 A9999 应得到“未找到”，具体回答措辞由模型生成。

工具读取的是 `orders.json` 中的演示数据，不是真实电商订单，也没有连接物流服务。

| 订单号 | 商品 | 状态 |
| --- | --- | --- |
| A1001 | 机械键盘 | 已发货 |
| A1002 | 无线鼠标 | 待发货 |
| A1003 | 显示器支架 | 已签收 |

## 可用工具

| 工具 | 参数 | 用途 |
| --- | --- | --- |
| `get_order_status` | `order_id` | 查询订单状态、物流、对应商品 ID |
| `search_products` | `keyword`、可选 `max_price` | 按名称或分类关键词搜索，可限制最高单价 |
| `get_product_details` | `product_id` | 查询商品价格、库存和规格 |
| `calculate_order_total` | `product_id`、`quantity`、`destination` | 检查库存并计算商品小计、运费和总价 |
| `get_after_sales_policy` | `topic` | 查询退货 `return`、换货 `exchange`、保修 `warranty` 规则 |

数据文件：`orders.json` 存订单，`products.json` 存商品，`store_rules.json` 存演示运费和售后规则。订单的 `product_id` 可以用于查询商品详情。全部是本地演示数据。

可以直接尝试：

```text
找一下 100 元以内的鼠标，有库存吗？
P1001 用什么轴，怎么连接？
买两只无线鼠标寄到上海，总共多少钱？
买一把机械键盘寄到新疆多少钱？
帮我查 A1001，再看看对应商品的规格和保修规则。
你们的演示退货规则是什么？
```

### 一个需要串联工具的问题

“买两只无线鼠标寄到上海多少钱？”的典型执行过程：

1. 模型请求 `search_products(keyword="无线鼠标")`。
2. 程序返回商品列表：P1002 是 79 元的无线鼠标，有库存；P1004 是 99 元的静音无线鼠标，库存为 0。
3. 模型根据结果选择有库存且名称匹配的 P1002，调用 `calculate_order_total(product_id="P1002", quantity=2, destination="上海")`。如果用户条件无法确定商品，应先询问用户。
4. 程序按规则计算：商品小计 158 元，普通运费 8 元，合计 166 元。
5. 模型根据结果组织回答。

这是有数据依赖的多轮调用：第二个工具的商品 ID 来自第一个工具的结果。程序没有写死“先搜索再报价”的流程，而是由模型根据工具描述和结果选择下一步。一次回复中的多个工具请求仍然在 Python 中逐个执行。

### 报价的演示业务规则

- 数量必须为 1 到 99 的整数，且不能超过库存。
- 普通地区运费 8 元，商品小计满 199 元包邮。
- 新疆、西藏运费固定 20 元，不参与包邮。
- 地区使用省级名称，例如“上海”“广东”。未配置的地区返回无法报价。
- 金额计算使用整数“分”，返回时换算成元。
- 报价不创建订单，也不扣减或预留库存。售后工具只查询虚构规则，不受理申请。

### 工具参数的校验与分发

`execute_tool()` 先用 `inspect.signature(function).bind(**parameters)` 检查当前函数需要哪些参数，拒绝缺失或多余参数，再由各工具函数校验参数类型和业务范围。

例如，报价函数拒绝负数数量、浮点数量和布尔值；搜索函数拒绝非法价格；售后函数只接受三个规定主题。JSON Schema 是给模型的接口说明，不能代替执行时的校验。

继续添加工具时，需要同步修改三处：`TOOLS` 中的接口说明、实际 Python 函数、`TOOL_FUNCTIONS` 中的函数注册。模型执行循环通常可以保持不变。若工具涉及写入或真实业务动作，还要考虑授权、持久化和重复执行问题。

## 一次工具调用如何完成

模型负责理解问题、选择工具、生成参数，并根据结果组织语言。Python 程序负责校验参数、执行函数和回传结果。订单文件负责提供数据。

**模型输出结构化的调用请求，由本地 Python 程序执行函数并读取订单文件，再把结果返回给模型。**

```text
用户：A1001 发货了吗？
  ↓
Python → 模型：聊天记录 + 可用工具说明
  ↓
模型 → Python：调用 get_order_status，参数为 {"order_id":"A1001"}
  ↓
Python：读取 orders.json，查到“已发货”
  ↓
Python → 模型：已有聊天记录 + 调用请求 + 工具结果
  ↓
模型 → 用户：你的机械键盘已发货，包裹已到达上海分拨中心，等待派送。
```

最后一句只是示意，实际措辞由模型生成。

## 对照代码阅读

所有核心逻辑位于 `main.py`，可以按下表定位，再阅读后面的调用步骤。

| 代码位置 | 关注的问题 |
| --- | --- |
| `get_order_status()` 等业务函数 | 不调用模型时，工具本身如何读取数据和计算结果？ |
| `TOOLS`、`TOOL_FUNCTIONS` | 工具接口说明如何对应到实际函数？ |
| `execute_tool()` | 如何解析参数、限制可调用函数并处理错误？ |
| `chat_with_tools()` | 如何将工具请求、工具结果和最终回答组成完整一轮？ |
| `main()` | 如何加载配置、接收输入和维护多轮对话？ |

### 1. 从独立的业务函数开始

`get_order_status(order_id)` 接收订单号，读取 JSON 文件，返回字典。

```python
get_order_status("A1001")
# {"found": True, "order_id": "A1001", "product": "机械键盘", ...}
```

它与 LLM 无关，可以直接运行：

```powershell
.\.venv\Scripts\python.exe -c "from main import get_order_status; print(get_order_status('A1001'))"
```

这里用文件模拟业务数据。以后可以把函数内部替换成数据库查询或 HTTP 请求，外层调用流程基本不变。

### 2. 用 Schema 描述工具接口

`TOOLS` 是发给模型的接口说明，包括：

- `name`：工具名称，程序用它找到对应函数。
- `description`：用途说明，帮助模型判断何时调用。
- `parameters`：JSON Schema，描述参数结构。
- `properties.order_id`：订单号必须是字符串。
- `required`：必须提供 `order_id`。
- `additionalProperties: False`：声明不接受额外参数。

Python 的函数实现不会随 `tools=TOOLS` 一起发给模型。模型看到的是接口说明。Schema 提供生成约束，程序仍要校验参数；不能假设模型输出永远正确。

`SYSTEM_PROMPT` 补充行为规则：订单信息要查询、缺少订单号先询问、查不到就如实回答。提示词帮助引导行为，实际执行范围由程序控制。

### 3. 将工具说明随请求发送

`chat_with_tools()` 请求模型时传入：

```python
tools=TOOLS,
tool_choice="auto",
```

`auto` 表示允许模型选择直接回答或请求工具。代码没有用“问题包含订单二字就执行函数”这样的关键词判断。

### 4. 识别结构化调用请求

模型可能返回如下结构，字段值仅为示意：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_demo_1",
    "type": "function",
    "function": {
      "name": "get_order_status",
      "arguments": "{\"order_id\":\"A1001\"}"
    }
  }]
}
```

注意 `arguments` 是包含 JSON 的字符串，不是 Python 字典，要先 `json.loads()`。此时 `content` 可以为空，因此必须先检查 `tool_calls`，再判断有没有普通回答。

这条请求来自模型，所以消息角色仍然是 `assistant`。程序要先把它完整加入历史，包括工具名称、参数和调用 ID。

### 5. 在 Python 中执行函数

`execute_tool()` 按以下顺序处理：

1. 检查工具名称是否在 `TOOL_FUNCTIONS` 白名单中。
2. 解析 JSON 参数并检查字段、类型和空值。
3. 执行 `TOOL_FUNCTIONS[name](**parameters)`。
4. 把函数返回的字典转换成 JSON 字符串。

`**parameters` 将 `{"order_id": "A1001"}` 展开成关键字参数，等价于 `get_order_status(order_id="A1001")`。

参数错误、文件读取失败等会变成包含 `error` 的工具结果，让模型知道失败原因。未知订单返回 `found: false`，这是正常的查询结果。

文件读取失败只返回通用提示，不把原始异常中的本机路径交给模型。命令行也不打印模型服务的原始异常或启动错误的完整堆栈，避免分享终端输出时带出账号信息和本机路径。正常工具日志仍包含查询参数和结果，应仅使用演示数据。

### 6. 用 tool 消息回传结果

```json
{
  "role": "tool",
  "tool_call_id": "call_demo_1",
  "content": "{\"found\":true,\"order_id\":\"A1001\",\"status\":\"已发货\"}"
}
```

`tool_call_id` 必须匹配前面请求的 `id`，用于说明“这个结果属于哪次调用”。一次请求可能查多个订单，因此每个调用都要有对应结果。

代码用 `for call in message.tool_calls` 逐个执行，即使模型一次返回多个调用，Python 目前也是顺序处理。

### 7. 带着工具结果再次请求模型

典型消息顺序是：

```text
system     行为规则
user       A1001 发货了吗？
assistant  请求调用 get_order_status（包含 tool_calls）
tool       对应调用的订单查询结果
assistant  最终自然语言回答
```

工具执行后进入下一轮循环。模型会看到工具结果，可以直接回答，也可以再请求工具。拿到没有 `tool_calls` 的文本回答后，本轮才结束。

为了限制反复调用，示例最多执行 5 轮工具，第 6 次请求设为 `tool_choice="none"`，让模型整理答案。若模型仍要求调用工具则报错。

## 与智能体循环的关系

这个程序已经包含一个最小的智能体循环：**观察上下文 → 决定是否调用工具 → 执行 → 观察结果 → 继续决策或回答**。

`messages` 保存当前进程中的对话上下文；`TOOLS` 描述能力；`TOOL_FUNCTIONS` 连接接口和实现；`chat_with_tools()` 驱动循环。更复杂的 Agent 会增加更多工具、任务规划、持久记忆和权限管理，但工具调用的核心协议与这里相同。

当前查询工具只读文件。每轮聊天先操作消息副本，整轮成功后才提交历史；API 出错时避免留下缺少配对结果的调用消息。这只是聊天历史回退机制，如果以后添加发送邮件、下单等有副作用的工具，还需要单独处理重复执行问题。

## 动手实验与自检

保持程序运行，先问 A1001 的状态。然后手动把 `orders.json` 中 A1001 的 `status` 改为“已签收”，并同步修改 `shipping`，再次要求“请重新调用工具查询 A1001”。

观察终端的 `[工具请求]` 和 `[工具结果]`。函数每次调用都会重新读文件，所以第二次结果会反映修改后的数据。这能直观看到：答案的数据来自工具执行，模型负责把结果组织成语言。

如果没有工具日志，说明这次模型没有请求工具。可以明确要求调用工具，并确认 `.env` 选择的模型支持 Function Calling。

实验结束后，将演示数据恢复原值，避免影响后续示例和测试。还可以直接调用 `calculate_order_total("P1002", 2, "上海")`，对照模型回答中的 166 元报价，区分业务计算与语言组织各自的职责。

自检：为什么 `TOOLS` 中写了函数名，程序仍然需要 `TOOL_FUNCTIONS`？为什么每条 `tool` 消息都需要 `tool_call_id`？如果模型返回错误参数，校验应发生在哪里？

## 常见问题

| 现象 | 检查方向 |
| --- | --- |
| 启动提示检查依赖或配置 | 确认使用本目录的虚拟环境，依赖已安装，`.env` 三个变量均已填写 |
| 普通聊天正常，查询却没有工具日志 | 确认模型支持 Function Calling，并明确要求查询演示数据 |
| 返回演示数据读取失败 | 确认三个 JSON 数据文件完整、格式正确且使用 UTF-8 编码 |
| 模型调用失败 | 检查网络、密钥权限、服务地址与模型是否匹配 |
